## How it works

1. **Cue.** A ground GPS relay hands the interceptor the target's position once,
   at launch. After that the link is dead by design.
2. **Rendezvous.** The interceptor flies to a point behind where it believes the
   target is and matches its speed, with the camera turned toward it.
3. **Track.** A camera on a Raspberry Pi 5 reads an AprilTag on the practice
   target. Bearing comes from the tag's position in the image, range from its
   size, and a Kalman filter estimates the target's position and velocity.
4. **Close.** A pursuit law flies the final approach, with closing speed capped
   so the interceptor can still stop. A missed pass aborts to a safe hover.

The guidance code in [`flight/`](flight/) runs unchanged on the Pi and has no
access to simulator ground truth. A neural-net detector that does not need the
marker is in development for the later phase.

The real flight code flies a simulated quad with a rendered camera against a
9 m/s crossing target. The chase now ends inside the 0.35 m contact radius on
6 of 8 flights, median miss 0.24 m. It took five test campaigns to get there,
each with its pass bar written down before flying. The biggest fix was a
two-line wiring bug: the filter was using the last commanded velocity instead
of the measured one. It would have flown on the real aircraft.

### Fast simulator with a realistic target

[`isim/`](isim/) runs the same flight code thousands of times against a vehicle
model fitted to 345 logged Gazebo flights. The target is a quad that pitches
and banks along its path with the tag bolted to its body. The runs include
vibration blur, shake, sun glare, and realistic errors in the interceptor's
own attitude, velocity and timing, all set to the worst-credible tier.

| Scenario (9 m/s target, approach from behind) | Inside 0.35 m | Median miss | Runs |
|---|:---:|:---:|:---:|
| Nominal | 91% | 0.12 m | 150 |
| Launch aim off by 20° | 73% | 0.20 m | 150 |
| Target 3 m higher than the cue said | 34% | 0.50 m | 150 |
| Target weaving | 32% | 0.53 m | 50 |

The height and weave cases are the open problems. Tilting the camera up 10° and
canting the tag down 12° brings the 3 m height case back to about 60%, and that
pair is now in the build spec. Source: [`isim/specs/tag_realism_v1.md`](isim/specs/tag_realism_v1.md).

### Earlier milestones

The project started as a PX4/Gazebo guidance study with scripted pass/fail
gates (M0 to M5, in [`scripts/`](scripts/)). Proportional navigation beat pure
pursuit by 4.6 to 7.6x in miss distance against a 2 m/s target, camera only.

## Hardware, October 2026

The airframe is assembled and has been powered on its 6S battery, props off.
The radio motor-cutoff switch is wired and verified. The Pi commands the flight
controller over a serial link, 300 of 300 setpoints at 19.5 Hz. The camera is
calibrated to 0.73 px RMS, and the real flight state machine has run end to end
on live camera frames at the desk. Calibration also showed the delivered lens
sees about 70 degrees, not the 118 the listing claimed. A tape measure agreed,
and a wider lens is on the parts list. First flights are next.

## Not done yet

- **No real flight.** Every miss number above is simulation.
- **Both simulators assume a perfect launch cue and no wind.** The GPS cue relay
  is built; its error in the field is not measured yet.
- **In Gazebo the tag is a flat board on a scripted mover.** The pitching,
  banking quad is modeled in the fast simulator, not rendered in Gazebo.
- **The markerless detector is early.** Retrained on real photos it reaches
  0.44 AP50 on held-out images (the simulator-trained version scored 0.0003).
  It has not flown.

## How the evidence is kept honest

- An automated test fails the build if guidance code reads simulator ground
  truth.
- Every published number traces to a logged run, a gate script, or one of 140+
  written design decisions ([`docs/decisions.md`](docs/decisions.md)).
- Tests are registered before flying: the configuration, the prediction, the
  pass bar, and what a null result would mean.
- Retractions are kept next to results. Early headline numbers that the
  project's own audits overturned are recorded in the contradiction ledger and
  dead-ideas list of [`docs/project_state.json`](docs/project_state.json).

The project's live state lives in that one file: stage status, constraints,
open contradictions, and a register that grades every input the system is
given rather than measures. It renders to a status board
([`docs/dashboard.html`](docs/dashboard.html)) and a generated systems model
([`docs/mbse.html`](docs/mbse.html)), and the tests fail if either drifts
from it.

## Run it

```bash
python3 -m venv --system-site-packages .venv && .venv/bin/pip install -r requirements.txt
scripts/run_tests.sh          # offline test suite + dashboard/model drift checks
```

The Gazebo gates (`scripts/check_m0.sh` to `check_m5.sh`) and Monte-Carlo
batches (`scripts/mc_batch.sh`) need Ubuntu 24.04 with PX4 SITL and Gazebo
Harmonic. `scripts/env/bootstrap.sh` sets up a fresh machine.
