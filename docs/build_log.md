# Project Log

A running log of how this project has actually gone, the process more than the results.

*Note for an AI organizing this log: the written contents should not be changed except for spelling errors and light formatting/structure cleanup (which I've sanctioned). The formatting of each entry may be adjusted, just not the core contents.*

## Pre-part work

With extensive planning and Claude Code usage, most software has been set up ready to install for the first of the test campaign. I started with identifying goals for the project, methodology for testing the goals, and the best way to go about AI usage in making a project with far too much software for myself alone manageable and realistic.

Extensive time was spent with project management, as project files quickly ballooned well above frontier context limits. Workflows, an extremely detailed project CLAUDE.md, and use of a Fable head were crucial for useful AI work. Furthermore, ensuring code would actually work was done via the use of a drone simulator, running as much of the code as possible to catch errors and logical faults I missed.

The biggest hurdle to overcome was the standard limitations of LLMs today, listed below with a significant example of each.

- **Overly agreeable sentiment** that would have a difficult time saying no to a certain methodology or project aspiration: The initial aspirations for building a visual Neural Network ready to use on the flight hardware I could afford, entirely with the simulator. Claude seemed to think it possible, but after extensive testing with the sim-built neural network I came to the conclusion we could not get around onboard compute constraints or sample size constraints (at least using simulator only and public datasets). Another good example of this was seeing intercept distance numbers that looked excellent, only to realize the sim didn't simulate vertical separation or vertical homing at all! Other sim measuring issues worked against me the other way, measuring intercept distance at the wrong time and frustrating me as to why numbers suddenly got so bad. Monitoring at least one run per sim batch on the GUI became important. Issues like these also quickly went away as Opus 4.8 left.
- **Context holes** overlooking important challenges: Definitely part of the learning curve orchestrating a project with so many moving parts. Something so simple as how I would mount the AprilTag that the seeker would track to the target drone, that I didn't consider until right as I was ordering parts. I quickly learned I was not nearly thorough enough in building diagrams and techniques to catch constraints in both hardware and software, and had to adapt quickly.
- **Context management:** Despite hundreds of prior hours spent at the head of agents, far less capable than Fable at context management, I still hit my limits with keeping important project details cached for models to consider. Striking a good balance of model guidelines while not overloading CLAUDE.md and other project management docs was a difficult time, and led me to regret not using Obsidian. I overcame this (and aforementioned constraint identification and resolve) primarily with a Claude-created interactive artifact that I could access from any device and track the status of each moving part of the project ([link to the artifact](https://claude.ai/code/artifact/eb5e40d1-c12a-4b87-bca0-589ad5af96fc)). Claude and myself would reference and update that before anything else when working a respective issue to ensure important holes wouldn't go uncaught. Keeping up with the latest ways to handle Opus and Fable in these regards were important as well as they shifted in context strategy considerably.
- **Actually using Fable:** My project is Fable safeguards' worst nightmare in nearly all regards, but also relied on its abilities heavily. The head agent, particularly for the first 2/3 of the software-only phase, would get knocked to the then-available Opus 4.8 within minutes of days-long work sessions. I initially worked around it with Fable subagents to review the work and attempt project housekeeping outside the scope of the actual intercept code development, which was a large inconvenience. Opus 5 was a significant upgrade in this regard as it gained many of the Fable abilities I relied on heavily. Once I worked through the majority of the interceptor code and shored up the project files, I got the head pretty good at using subagents for all potentially flagged work, meaning at worst Opus 5 would handle a small part of the development while retaining Fable's superior management. (This was token expensive, but worth it as I heavily reduced needing to redo elements.)

Solving or reducing each of these issues naturally helped the others as well, which made project work get far more efficient and usable rapidly and exponentially, something I valued hugely and allowed me to retain motivation despite the setbacks. Ordering parts was relatively straightforward: I organized what I expected to have to buy, turned Claude loose on a build order and cowork session to load carts, and carefully scrutinized the selections against my own with the help of another detached Claude session evaluating constraints I had found against selections. This session was also the most important for handling the cost constraint against real hardware I needed. The careful picking allowed me to get a final parts list superior to both my own and Claude's, although it was reassuring to know either would have probably worked great. The biggest assets I came into the project with were core understandings of how LLMs work, and knowing exactly which questions to ask as work went on to identify gaps, programs I should be using, tools, and being determined to understand the workings of each subsystem within the project.

## Hardware-arrived work

Getting hardware made me feel like a kid on Christmas, finally getting to put what I had been working on into actual things and getting to spend time doing the satisfying work of seeing my choices actually work and come together. Claude was a lovely work assistant when I was unsure of how exactly parts would go together. Most of the initial build phase went smooth; however, I ran into troubles with some connectors on the Pixhawk 6C selected not working with the DuPont cables I needed for the Raspberry Pi interface (this is on the interceptor side of the hardware). Some splicing, heat shrink, and wiring diagrams Claude found made this a 5-minute fix that worked like a charm. I learned about safe handling of the lithium polymer batteries used as well. Raspberry Pi software loading was a breeze; once I got it on my local network I used SSH and my Claude CLI connected and handled it all beautifully (with a brief final code review). Pixhawk flight software was also straightforward.
