## ADR-0081 — real_flight.py: the onboard flight state machine (SITL-verified skeleton)

- **Context.** seeker_loop.py implemented only the terminal; there was no coded-dash executor or
  launch/standby logic on the real airframe. docs/launch_mechanism_plan.md L1 names this the plan's
  one real build item, fully SITL-testable with zero new hardware. Built this session (Opus 5 worker).
- **State machine.** STANDBY -> (operator GO edge) -> CODED_DASH -> (5 consecutive fresh detections)
  -> ENGAGE -> BREAKOFF -> SAFE (absorbing). Every transition guarded + logged; a setpoint is emitted
  on EVERY tick in EVERY state (PX4 drops OFFBOARD on a ~0.5 s stream gap). Composes seeker_loop's
  terminal + flight.guidance's accel-aware lead (ADR-0080) -- imports, does not duplicate.
- **Key decisions:** (1) Trigger = ELRS aux via MAVLink RC_CHANNELS through MAVSDK mavlink_direct
  (rc_status has no per-channel accessor in MAVSDK-Python; verified). (2) GO bit edge-triggered +
  hysteretic + REFUSES a switch already HIGH at boot (no boot-dash). (3) FAILSAFE ASYMMETRY -- link
  monitored in STANDBY ONLY; post-GO link loss is deliberately IGNORED. This IS the jam-resistance
  claim (constraint no-datalink): kill the TX right after GO and the camera-only terminal must finish
  unaided. Both halves tested. (4) A GO with a failed arm gate ABORTS to SAFE (not silently dropped).
  (5) Dash bound = time (mirrors the sim's max-s) + optional dead-reckoned distance; timeout -> SAFE,
  never a blind continue. (6) Aim = accel-aware lead (ADR-0080) default, --dash-heading-deg override;
  bearing latch built but default OFF (gated on bench intrinsics + measured 1-sigma bearing). (7)
  Latch-once ENFORCED (raises on 2nd write) + an --audit that proves from the AST exactly one
  dash-heading set site.
- **Honesty.** --audit (AST, not text): 0 ground-truth identifiers, 0 simulator imports, dash heading
  latched at exactly 1 site; inputs are camera pixels (ENGAGE only), own-state EKF, pre-flight
  constants, and ONE arm/kill bit (TriggerState cannot carry target info). Wall clock is
  time.monotonic() only (a GPS time-sync step would corrupt the dash ramp).
- **Verification.** Offline: 47 unit tests + a parity test that imports m4_intercept.py and asserts the
  handoff streak agrees case-for-case; full suite 311 passed / 2 skipped. SITL (this session): the gate
  scripts/check_real_flight_sitl.sh booted headless PX4 + gz_x500 and drove STANDBY->CODED_DASH->ENGAGE
  ->BREAKOFF->SAFE, 327 setpoints, OFFBOARD entered, heading latched, clean land+disarm, 0 orphans --
  PASS (logs/real_flight_sitl_20260724T233259Z.log).
- **NOT flight-ready -- builder review needed.** All safety-critical HW constants are tagged
  TODO-BUILDER (RC channel index/PWM endpoints/link timeout; standby alt/tol + hover endurance; real
  dash speed/accel; terminal/breakoff ranges; PX4 geofence + kill-switch + battery failsafe, which this
  module does NOT touch). Two honest scope gaps: update_recede_streak omits m4's streak_start_range
  magnitude check (slow-drift past-CPA risk, port-before-flight); the own-prop phantom-streak residual
  is inherited from the sim and is designed out in HARDWARE (nose-cantilever mount), not here.
- **Date.** 2026-07-24.

## ADR-0082 — One burn model, one measured frame rate: correct the placard-sizing gate

- **Context.** ADR-0079 adopted the conservative run-length streak burn in
  `tripod_score.gate_verdict`. The full project review (2026-07-24) found that
  `scripts/seeker/validate_autolabel_sim.py:tripod_gate()` — **the function that produced the
  published placard-sizing threshold and the 0.35 m recommendation** — still used the REJECTED
  mean-rate burn, at a hardcoded, unsourced `STREAM_FPS = 30.0`. So the codebase carried two
  different burn models and the optimistic one sized the hardware.
- **Decision.** (1) `validate_autolabel_sim.tripod_gate` now uses the identical run-length model
  (parity asserted numerically against `tripod_score._streak_burn_frames`) and takes the frame rate
  as a parameter; `STREAM_FPS_BAND = (30, 20, 14)` documents the credible range (as-published /
  deployed loop / measured tag rate) so the sizing report prints a BAND, not a single number.
  (2) The **placard size is UNCHANGED at 0.35 m tag / 0.45 m sheet** — it was already the carry
  limit, so no larger option exists without a different target airframe. (3) **`quad_decimate=1.0`
  (full-res decode) is promoted from "reclaim lever" to the PLANNED tripod-day capture setting**:
  it is the only configuration that clears the gate at 30/20/14 fps, whereas the deployed `qd=2.0`
  clears only at 30 fps.
- **Numbers.** Corrected threshold (t_go ≥ 0.5 s, 9 m/s, k=5), p=0.9: **6.58 m @30 fps, 7.62 m
  @20 Hz, 8.96 m @14 Hz**. The 0.35 m placard predicts 7.10 m at `qd=2.0` (PASS only at 30 fps) and
  8.97 m at `qd=1.0` (PASS at all three).
- **Why it matters.** The gate authorizes a ~$740 purchase. An optimistic burn at an invented frame
  rate could green-light an order the data does not support — or, with the bin-edge defect fixed the
  same day, red-light one it does. The frame rate is now a MEASURED input (`pi_capture` records
  `stream_fps` + a p10 slow tail; `tripod_score` returns UNCERTAIN rather than inventing one).
- **Honest scope.** This does not falsify the placard choice; it removes the margin that was never
  really there and names the one unmeasured input (achieved Pi capture rate) the decision hinges on.
  The tripod day remains the authority.
- **Date.** 2026-07-24.

## ADR-0083 — Adopt a +5° empirical aim trim for the coded dash (MEASURED, not derived)

- **Context.** The aim-error sweep (built to test whether the camera earns its handoff) produced a
  second, more valuable result in its CONTROL column: the open-loop dash-only miss is minimised NOT
  at the accel-aware lead's own solution but ~5° beyond it. Measured curve, dash-only, seed 123:
  **0° → 0.71 m, 2.5° → 0.54, 5° → 0.43, 7.5° → 0.69, 15° → 1.43**; parabola vertex **+4.5°**.
- **Replication (the project's statistics rule).** Disjoint seed 777: 0° → 0.57, +5° → 0.52, better
  on 6/8 paired. The seed-123 magnitude (−0.28 m) was optimistic; the second seed corrected it — the
  documented failure mode of single-seed effects. **Pooled n=16 (seeds 123+777, paired by run_idx):
  +5° better on 14/16, one-sided sign-test p = 0.0021, paired delta median −0.248 m.** This clears
  the pre-registered adoption bar (≥13/16) in `docs/flight_plan_candidates.md`.
- **Decision.** Adopt +5.0° as the CHARACTERIZED aim trim for the canonical line@9 + accel-aware-lead
  configuration, exposed as a NEW, explicitly-named flag `--dash-aim-trim-deg` (default 0.0,
  byte-identical when absent; 321 tests pass). It is mechanically identical to the existing
  `--dash-heading-err-deg` but kept SEPARATE because that flag *injects error* while this one
  *applies a correction* — a log must never be re-read months later with the two confused.
- **What it is NOT — the honest boundary.** It is **MEASURED, NOT DERIVED**. The mechanism hunt found
  a real defect (the solver assumes a = 10 m/s² while the measured pre-CPA effective accel is
  ~3.1 m/s²; by CPA it predicts 22.2 m of travel where the vehicle covers 8.2 m), but substituting
  the measured profile swings the heading 30-70° while the empirical optimum is only ~5° away — the
  naive "physically derived" fix would have made the aim dramatically worse. At CPA the interceptor
  has covered 8.2 m against the target's ~19.7 m, so the miss is dominated by target motion and is
  SHALLOW in heading near the optimum: a profile fit and an aim fit answer different questions.
  Therefore the trim is deliberately NOT baked into `collision_lead_heading_accel` — dressing an
  empirical constant as physics is this project's signature failure mode.
- **Why it matters.** The corrected 5-inch ram envelope is ~0.36 m (contract stage `kill`). The trim
  takes the open-loop dash from 0.71 m to ~0.43 m pooled — and the r2l cell to **0.33 m, inside the
  envelope** — with no perception, no hardware, and no camera. It is the only measured path into
  kill range currently in hand.
- **Obligation on the real build.** The trim is a per-configuration constant, not a law. It MUST be
  re-measured on the real airframe from the first dash ULog (`build_plan` L9), and the
  a = 10-vs-3.1 parameterization defect re-checked there, before any trim value is flown.
- **Date.** 2026-07-24.

## ADR-0084 — RATIFIED: the ram/kill radius is 0.35 m, derived from the ordered 5-inch airframe geometry (builder asked for the arithmetic, 2026-07-25)
- **Context:** Every Pk claim in the project was scored against a 0.5 m ram radius (ADR-0014/0025). The 2026-07-24 full review flagged that 0.5 m was a **7-inch** heritage number, while BOTH ordered aircraft are **5-inch** (interceptor GEPRC Mark5 Pro 5"; target TBS Source One V6 / Mark4 5") — so the true contact envelope is tighter and the whole headline bar was quoted against a radius the hardware cannot deliver. The builder asked me to run the arithmetic from the ordered hardware and the payload/size and ratify the number.
- **The arithmetic (contact envelope = center-to-center CPA at which any prop/frame contact is geometrically possible = sum of the two aircraft's half-spans):**
  - Shared prop: HQProp 5.1" tri-blade → prop diameter = 5.1 × 25.4 = **129.5 mm**.
  - Interceptor Mark5 Pro 5": wheelbase (diagonal motor-to-motor) 226 mm → tip-to-tip span = 226 + 129.5 = **355.5 mm**; half-span (center→prop tip) = (226+129.5)/2 = **177.8 mm**.
  - Target Source One V6 5": wheelbase 220 mm → half-span = (220+129.5)/2 = **174.8 mm**.
  - **R_contact = 177.8 + 174.8 = 352.5 mm ≈ 0.353 m.**
  - Provenance check of the retired 0.5 m: two 7-inch aircraft (7" prop 177.8 mm, ~300 mm wheelbase) → half-span 238.9 mm → 2×238.9 = 477.8 mm ≈ 0.48 m ≈ the old 0.5 m. Confirms 0.5 m was the 7-inch number.
- **Payload / size feasibility (the other half of the builder's question — does the 5-inch airframe carry the seeker it needs?):** dry mass with the full ordered seeker stack (Mark5 frame+hw 120 g, 4× XING2 2207 132 g, Tekko32 ESC 13 g, 6C Mini 35 g, PM02 30 g, M10 15 g, RP3 RX 3 g, Pi 5 8GB 46 g, active cooler 25 g, OV9281+M12 15 g, BEC 10 g, printed tray 35 g, wiring/standoffs 30 g, prop set 16 g) ≈ **525 g**; + 6S 1500 mAh pack 245 g → **first-kill AUW ≈ 770 g** (AprilTag baseline, no Hailo); + AI HAT+ 20 g → **≈ 790 g** for the markerless phase. Against the 950 g design AUW that leaves **~160–180 g** headroom. Static thrust 4 × ~1.5 kg = 6.0 kg → **T/W ≈ 7.8:1 at 770 g / 6.3:1 at 950 g.** The 5-inch airframe carries the full seeker payload with margin; **payload is NOT the size-limiting factor**, so there is no payload-driven reason to go to a larger (wider-envelope) airframe.
- **Decision:** RATIFY **R_ram = 0.35 m** as the go-forward kill/scoring radius (rounded down from 0.353 m — conservative). `scripts/field_score.py` `DEFAULT_LETHAL_RADIUS_M` changes 0.5 → 0.35. The 1.5 m "net-class" radius is unchanged (that's a different, forgiving mechanism). Prior measured Pk-vs-radius tables (ADR-0025/0029/0064, the 0.5 m columns) STAND as history — this ADR sets the default and the forward bar, it does not rewrite past measurements.
- **Consequences swept the same turn (this is a re-derivation, not a constant change):**
  - `docs/launch_mechanism_plan.md` §3 aim-error budget re-derived from the dash_cpa ballistic model's own miss-vs-aim table (interpolated, not naive tan): tolerance for the ram tightens **±3.0° → ±2.4°** (nominal column) / **±4.5° → ±3.0°** (worst column); trigger-timing budget: every 100 ms of latency ≈ 3° now EXCEEDS the ±2.4° budget (~80 ms consumes it). The static camera bearing latch (~0.1–0.5°) remains the only aim method that clears it; a boresighted red-dot (1–2°) goes from "marginal" to "marginal/no".
  - `docs/kill_mechanism.md`, `docs/launch_mechanism_options.md`, `docs/flight_plan_candidates.md`, `docs/demo_plan.md`, `demo_out/README.md` ram-radius quotes updated to 0.35 m / ADR-0084 (historical measured-data columns left intact with a footnote — not silently relabeled).
- **The one physical lever if 0.35 m proves too tight:** the only way to widen the envelope is a physically bigger interceptor (a 7" would restore ~0.48 m but is heavier/slower, a Tier-2 airframe-class decision). This is NOT triggered by payload (which fits the 5") — it would only be triggered by the tripod/kill evidence showing the terminal cannot deliver 0.35 m. Held until that evidence exists (and note: the "camera terminal can't earn a metre at 0.35 m" inference is downstream of the frozen_vworld sim defect fixed 2026-07-25, so it must be re-measured before it can argue for a bigger airframe).
- **Why:** the builder asked for a hardware-grounded number, not a vibe. 0.35 m is pure geometry from the ordered parts, conservative, and traceable. Ratifying it unblocks the Tier-2 order decision on an honest premise and stops every visible Pk surface quoting a radius the aircraft can't achieve. Supersedes the 0.5 m default of ADR-0014/0025.

## ADR-0085 — #16 vertical channel + altitude datum: arm-point local datum + hard AGL floor (head decision under the builder's 2026-07-25 "do every item" directive; flag for builder review)
- **Context:** The build queue carried "#16 vertical channel + altitude datum" as a five-word label with the question never written down (named in the audit as a decision that would evaporate). The real question: what altitude REFERENCE does the outdoor interceptor's vertical channel hold to, and how is the vertical commanded across standby → dash → terminal?
- **Options:** (a) barometric altitude (drifts with weather, no absolute datum); (b) GPS/MSL altitude (absolute but ~1–3 m noisy, and the target's GPS-alt is independently noisy); (c) **EKF local altitude referenced to the ARM point** (the takeoff datum), matching the sim's ENU-origin-at-start convention, with the terminal vertical driven by the camera elevation angle within a safety band.
- **Decision:** (c). Hold a commanded altitude **relative to the arm-point datum** through standby and the coded dash (consistent with the sim's world-ENU-origin-at-start frame, so guidance transfers). In the terminal, the vertical channel follows the camera-derived target elevation within a bounded band, floored by a **hard AGL minimum** (a `min_agl_m` safety floor below which the vehicle will not descend regardless of the seeker) and ceilinged by the site altitude limit. The two aircraft's altitude logs are reconciled to a common datum at scoring time via `field_score`'s clock/datum sync — the datum for the KILL geometry is relative (interceptor-to-target), so absolute MSL is not required for the binary-kill criterion.
- **Why:** the arm-point datum is the only reference the sim validated and the only one that needs no absolute survey; it keeps the vertical sign conventions identical to the flown guidance. The hard AGL floor is the flight-safety backstop that prevents a bad seeker elevation from flying the interceptor into the ground. Absolute datum is deferred to the (cut) RTK path — not needed for a binary kill. **Builder review flag:** if the site requires an absolute ceiling referenced to MSL (some FRIA/Part-107 constraints), add an MSL clamp alongside the AGL floor.

## ADR-0086 — #22 post-GO OFFBOARD-loss: implement FAILSAFE 7 (BREAKOFF → SAFE), replacing the phantom "ADR-0081 addendum" (head decision under builder 2026-07-25 directive)
- **Context:** `flight/deploy/real_flight.py` defined FAILSAFEs 1–6 and 8 but 7 was unused, and a comment (~:1731) pointed at "the open ADR-0081 addendum" that never existed. The hazard: after GO (past standby), if the OFFBOARD setpoint stream / control link is lost mid-engagement, no safe behavior was defined — a blind continued dash is the worst outcome.
- **Decision:** Implement **FAILSAFE 7** — detect loss of the OFFBOARD setpoint stream (stale setpoint / offboard heartbeat gap beyond a bound) during DASH/ENGAGE and transition to **BREAKOFF → SAFE** (hover, land requested), never a blind continued dash. (Implementation landed 2026-07-25 in the same push; see `flight/deploy/real_flight.py` FAILSAFE 7 and `docs/kill_day_protocol.md` safety geometry.)
- **Why:** props-on flight safety — an interceptor that loses its control link near the target must remove itself from the engagement, not continue open-loop toward a second aircraft. Consistent with the no-datalink architecture (the dash is open-loop by design, but a DETECTED loss of the offboard stream is still a defined SAFE trigger). Closes the dangling phantom-ADR reference. **Builder review flag:** ratify the real timeout on the props-off bench (6C Mini) before the first kill.

## ADR-0090 — The seeker was running at 30 fps because of an inherited picamera2 default, not a hardware limit: make the frame-duration cap an EXPLICIT, MEASURED parameter (head decision, 2026-07-26 bench)
- **Context:** skr-07 (the Pi 5 sustained-fps thermal soak, protocol §7.3) is the money gate's `1/fps` divisor and had never been run — no harness existed. Building one (`scripts/seeker/pi_fps_soak.py`) surfaced something the bench was not looking for: at `quad_decimate=2.0` the Pi 5 was decoding AprilTags at ~117 fps of throughput while the camera delivered **exactly 30.0 fps**. The OV9281 advertises 143 fps at 1280×800, so 30 was not a sensor limit and not a compute limit — it was picamera2's inherited `FrameDurationLimits` default, which neither `pi_capture.py` nor `flight/deploy/seeker_loop.py:PicameraSource` ever set. Nobody chose 30 fps; it was never recorded as a parameter, and `streak_burn_derivation.py` hard-codes `FPS = 30.0` while `tripod_test_protocol.md` §7.3 offers "AprilTag ~30 fps CPU-real-time" as the anchor to compare against — so the number had quietly become a project-wide assumption traceable to no measurement.
- **Options considered:** (a) leave the default and quote 30 fps as the gate divisor; (b) uncap to the sensor maximum (143 requested); (c) make the cap an explicit, recorded, measured parameter and choose the operating point on evidence.
- **Decision:** **(c).** `--target-fps` is now a first-class recorded parameter of the bench (the same treatment `quad_decimate` received, and for the same reason: an unrecorded default silently sets a number the ~$740 verdict turns on). Measured on the real Pi 5, 15-min soak, qd=2.0: **sustained 108.6 fps** (up from 30.0), 46.3 → 56.8 °C, max 59.5 °C, `throttled=0x0` throughout, and steady-state ≈ cold-start (108.6 vs 108.2) — i.e. **no thermal derating with the active cooler fitted**. CPU cost measured passively: 1478 s of CPU over 613 s elapsed = **2.41 of 4 cores (60%)**, decode only.
- **Recommended operating point — 60 fps, NOT uncapped.** The burn model is `R_streak_burn = (E[T]/fps)·V_closing` (ADR-0079), so the gain is strongly concave: at p=0.7, V=9 m/s the burn falls 4.95 m → 2.47 m going 30→60 fps, but only 2.47 m → 1.33 m going 60→108.6. The first doubling buys ~2.5 m for ~30% of the SoC; the rest buys ~1.1 m for another ~30%, and the flight Pi must also carry guidance, EKF, MAVSDK and logging on the same four cores. **Ratify against a measured 60 fps arm before flying it** — the intermediate rung has not been soaked yet.
- **Why it matters beyond the bench:** this is not a bench artifact. `PicameraSource` — the class that flies — sets exposure and gain but no `FrameDurationLimits`, so the deployed seeker inherits the same cap. `scripts/seeker/probe_flight_frame_rate.py` tests that class directly (rather than a copy of its setup) and is queued to run.
- **What this does NOT claim.** The 108.6 fps is the **AprilTag** decode path, and it is **not gate-eligible**: the soak ran with no tag in view, which understates decode cost and so overstates fps — the flattering direction, which is why `pi_fps_soak.py` refuses it. `scripts/seeker/tag_decode_cost.py` was written to bound that error and has not run yet. Separately, the "5-streak unformable at p=0.4417" result in `detection_tracking_methods.md` §A.4 is the **NN's** held-out recall on the **markerless** path, not the tag path; whether the frame-rate finding touches it at all depends on the CPU-YOLO rate (arm 3, running). **Do not merge the two pipelines' numbers.**
- **Follow-ups:** re-earn the constants that assumed 30 fps (`streak_burn_derivation.py:FPS`, protocol §7.3's anchor, §A.4/B.3 tables) — a threshold validated at one operating point is not validated at another; run the 60 fps arm, the tag-cost pairs, and the flight-class probe; then re-quote the gate.

### ADR-0090 addendum 1 (2026-07-26) — the DEPLOYED class is confirmed capped; qd=1.0 corrected to 38.2 fps
- **The cap is in the flight path, measured, not inferred.** `scripts/seeker/probe_flight_frame_rate.py` instantiates `flight/deploy/seeker_loop.py:PicameraSource` **itself** (not a copy of its setup) and times it: **as flown 30.048 fps** (p10 28.7), **cap lifted 114.893 fps** (p10 101.3), **speedup 3.82×**, `capped=true`, exposure 994 µs applied. So the seeker that flies inherits picamera2's frame-duration default. The original ADR said "probably capped too"; it is now measured.
- **qd=1.0 corrected: 38.2 fps, not 40.3.** The first qd=1.0 arm returned `tag_frac=0.44` and refused itself — the on-screen tags were being blanked mid-soak by `OLED Care Screensaver.scr`, a vendor screensaver on the ordinary Windows idle timer (a display wake-lock does not stop a screensaver). Re-run with the idle timer held off: **38.2 fps, `tag_frac=1.0`, gate-eligible**, 60.0 °C max, no throttling. The corrected figure is **lower**, as it must be — real tags cost decode time — and it supersedes 40.3 everywhere.
- **The tagless/tagged bracket, and why the refusal earns its keep.** qd=2.0 tagless read 108.6 fps; tagged, 96.6. The missing tag inflated the rate ~12%, in the flattering direction for a purchase gate — which is exactly what `pi_fps_soak.py` refuses to certify. The bracket is the honest statement: the flight case, with one distant placard rather than eight close ones, should sit at or above the tagged figure.
- **Thermal margin is an INDOOR margin (builder's question: does the drone's airflow help?).** It does, but it is the wrong worry. Flight is seconds and the soak is 750 s, so no engagement approaches the thermal severity of the bench; dash and prop-wash convection only add margin. The binding case is **ground standby** — armed on the launch plate in sun, no airflow, inside an enclosure the free stream never reaches. Bench ambient (builder-declared, unmeasured) ~26.7 °C / 80 °F in a warm machine room, which makes the bench *more* representative, not less. Projected to a 35 °C field day (estimate, assumes SoC tracks ambient 1:1): tag arms ~66 °C (**~14 °C margin**), CPU-YOLO ~75.5 °C (**~4.5 °C**). Solar gain on a dark airframe is additional and is not in that projection. Soft throttle is 80 °C; the 50/60/67/75 trips on `thermal_zone0` are **fan-curve steps**, not throttle points.
- **Overclocking: NO (builder asked, given no throttling).** The burn model is concave and we are past the knee, so a ~25% overclock buys ~0.30 m at qd=2.0 and ~0.7 m at qd=1.0, and moves CPU-YOLO 6.09 → ~7.6 fps when ~30 is needed — it rescues nothing. Against that: more current on a tight flight power budget, instability/SD-corruption risk on a flight-critical computer, and more heat exactly where margin is thinnest. **We already have a compute SURPLUS and are choosing to discard frame rate; the answer is to spend it on `quad_decimate=1.0` (range and incidence cone), not on clock.** Revisit only if tripod day forces qd=1.0 *and* its 38.2 fps proves binding.
- **Stale code on the bench is a recurring hazard, now hit twice.** The Pi's checkout was behind on `pi_capture.py` (publishing an unbounded decode rate) and again on `flight/` (missing the exposure pin, which broke the probe until synced). The bench must run the repo's code or it certifies something else; worth a version assertion in the bring-up pack.

## ADR-0091 — The M10 lands on GPS2, not GPS1: the GPS is a param change, the COMPASS is a bus the firmware never scans (bench decision, 2026-07-27)

- **Context.** At the bench the builder found the Holybro M10's cable is **6-pin**, so it
  physically fits only **GPS2**; GPS1 on the Pixhawk 6C Mini is a 10-pin connector. The
  `brn-02` step, `configs/px4_6cmini/README.md` and `bench.params` all assumed GPS1.
- **What is actually on each port** (Holybro 6C Mini port pinout, verified 2026-07-27):
  GPS1 = 10-pin JST-GH — VCC, TX1, RX1, **SCL1/SDA1 (I2C bus 1)**, SAFETY_SWITCH,
  SAFETY_SWITCH_LED, IO_VDD_3V3, BUZZER-, GND. GPS2 = 6-pin JST-GH — VCC, UART8_TX,
  UART8_RX, **I2C2_SCL/SDA (I2C bus 2)**, GND.
- **The GPS half is trivial.** `GPS_1_CONFIG` is a generic serial-port assignment; setting
  it to **"GPS 2"** in QGC (plus `SER_GPS2_BAUD` = Auto) makes the receiver on GPS2 the
  PRIMARY GPS. Using `GPS_2_CONFIG` instead would leave `GPS_1_CONFIG` pointed at an empty
  port and a permanently failing primary — do not do that.
- **The COMPASS half is the finding, and it is silent.** PX4 v1.16.0
  [`boards/px4/fmu-v6c/init/rc.board_sensors`](https://github.com/PX4/PX4-Autopilot/blob/v1.16.0/boards/px4/fmu-v6c/init/rc.board_sensors)
  starts exactly two ist8310 instances: `ist8310 -X -b 4 -a 0xc start` (the board's
  internal mag) and `ist8310 -X -b 1 -R 10 start` (GPS1's I2C). **Bus 2 is never probed**,
  so a compass on GPS2 simply does not appear — indistinguishable at the QGC surface from
  a dead module or a bad solder joint. This is exactly the failure class the project's
  fail-closed rule exists for: an absent measurement that reads as a hardware fault.
- **Options.** (a) `ist8310 -X -b 2 -R 10 start` in `/fs/microsd/etc/extras.txt` — sourced
  by `rcS` at line 584, *after* `sensors start` (line 350), so the late instance must be
  verified, not assumed. (b) A 6→10-pin GPS cable to move the module onto GPS1 (~$5) —
  puts it on the probed bus with the documented `-R 10` rotation. (c) Accept the internal
  ist8310 on bus 4 for bench work.
- **Decision.** **(c) for the bench now, (b) for flight.** `brn-05` never arms and needs no
  GPS fix at all (see the corrected note in `configs/px4_6cmini/README.md`), so nothing on
  the bench is blocked. An external mag away from the power wiring is worth having on the
  airframe, and a cable is cheaper and less fragile than an SD-card startup script that
  silently stops applying if the card is reformatted. (a) is the fallback if the cable is
  slow to arrive — verify with `ist8310 status` in the MAVLink console, never by assuming.
- **Second consequence, logged now so it does not surprise the airframe build.** This M10
  has **no safety switch** — those are GPS1 pins 6/7 and this module does not carry them.
  `bench.params` sets `CBRK_IO_SAFETY = 0`, which *restores* the safety-button arming gate,
  and PX4IO advertises `safety_button` whether or not a button exists. So at the first
  props-off ARM test the board will refuse with "Press safety button first" and there will
  be no button to press. Fix then, knowingly: either add a switch or set `CBRK_IO_SAFETY`
  back to 22027. Not a bench blocker (nothing arms in `brn-05`), and `README.md` §3's
  claim that "the M10 (with its safety switch) on GPS1" will satisfy it is **wrong for the
  module actually in hand**.
- **Date:** 2026-07-27.

## ADR-0092 — Motor screws are a load-bearing UNRECORDED assumption: M3×6 into a 6 mm arm is zero thread engagement (bench decision, 2026-07-29)

- **Context.** The EMAX ECO II 2207 motors arrived and the builder's reasonable assumption
  was "the 6 mm screws." Until today the build carried **no fastener line item anywhere** —
  not in `build_tab.target.parts`, not in `bom_tiers` — i.e. it silently assumed "the
  motor's included screws fit the frame." They do not, in the dangerous direction.
- **The arithmetic.** TBS Source One **V6** arm thickness is **6.0 mm** (TBS's own spec and
  CAD; note V4-and-earlier were thinner, so older Source One build guides mislead here).
  Thread engagement = screw length − 6.0 mm:
  **M3×6 → 0.0 mm** (the motor is held by nothing), M3×7 → 1.0, **M3×8 → 2.0**,
  M3×10 → 4.0, M3×12 → 6.0 (into the stator).
  EMAX ships 5× M3×8, 5× M3×7 and 5× M3×6 per motor — M3×8 being the longest is a strong
  hint that EMAX considers 8 mm this motor's safe maximum.
- **Decision.** **Use the included M3×8**, snug + blue threadlocker on the tip, torqued with
  the short arm of the 2.5 mm hex key. 2 mm of M3 in aluminium is ~4 threads and the carbon
  arm fails before the thread does; the real risk at that engagement is backing out under
  vibration, which threadlocker plus a pre-flight wiggle check covers. **M3×10 only if** a
  bench depth probe shows ≥4.5 mm of clear thread — the ECO II 2207's usable thread depth is
  **not published** and could not be confirmed from any source.
- **Why it is graded `unmeasured`, not `measured`.** Two quantities remain unverified: the
  motor's clear thread depth (unpublished), and whether the V6 arm is counterbored on its
  underside at the motor pad (TBS's 2D DXF shows no counterbore, but the arm's motor-mount
  detail is 3D geometry we could not measure). A counterbore would *reduce* effective
  thickness and *increase* engagement — which only reinforces M3×8.
- **The hazard, both ways.** Too long: the tip presses into the stator windings, and because
  carbon fibre is **conductive**, nicked enamel shorts a motor phase to the whole airframe —
  presenting as one hot motor, oscillations no tune fixes, then a burnt motor and possibly an
  ESC FET. A screw that merely *touches* enamel passes a meter test today and wears through
  in flight. Too short: threads strip under prop torque and a motor departs the arm with a
  5-inch tri-blade attached.
- **Mandated check (this is the part that does not depend on any number above being right).**
  Per motor, meter on continuity: **baseline before mounting** — wire↔wire beeps roughly
  equally across all three pairs, and every wire↔bare metal must **not** beep. Mount snug
  with **no threadlocker**, then re-test every wire → each screw head and every wire → the
  carbon arm: **any beep = a screw is in a winding, back it out.** Hand-spin the bell and
  compare to baseline for grind or tick. Log all four motors. Only then threadlock.
- **Also ratified:** motor leads are **not cut** until the ESC is in its final position.
  Derived from the ordered geometry, only ~20–25 mm of the supplied 120 mm leads is spare
  (~95–100 mm needed: 120 mm shaft-to-centre, leads exiting ~13 mm inboard, nearest pad
  ~21 mm from centre on a 30.5 mm board, ~10 mm rise) — *[DERIVED estimate, pending the real
  ESC in place]*, which is far less margin than the "cut half off" habit assumes. Phase order
  is irrelevant (direction is set in software), so there is nothing to plan by cutting early.
- **Date:** 2026-07-29. Sources: TBS Source One V6 product spec + `tbs-trappy/source_one`
  CAD/BOM · EMAX ECO II 2207 store page (16×16 M3, 120 mm 20 AWG, in-box screw list) ·
  oscarliang.com motor-screw winding check and threadlock guidance.

### ADR-0092 addendum (2026-07-29) — threadlocker is risk mitigation, not airworthiness; and an UNMARKED screw cannot be "checked"

The builder mounted the motors on the included **M3×8** (confirmed working) and asked,
correctly, whether threadlocker is mandatory or whether periodic inspection would do.

- **Blue is the right grade.** Loctite **242 / 243** (medium, removable). **Never red**
  (271/272) — permanent, needs heat, and motor replacement is routine maintenance on this
  airframe. Apply a dab to the screw **threads**, not into the hole; excess wicking toward
  the bearing is its own failure. **Full cure is ~24 h** (handling ~10 min), so it has to be
  done the night before a flight day, not on the field. Re-apply fresh every time a screw
  comes out.
- **Not strictly required to fly.** The honest position: threadlocker does not make the
  joint airworthy — 2 mm of M3 in aluminium is ~4 threads and the carbon arm fails before
  the thread does. What it buys is protection against **backing out under vibration**, which
  is the actual observed failure mode, and the margin is thinner at 2 mm engagement than on
  a build with 4 mm. This airframe is also the one the contract designates as the
  hard-landing taker.
- **THE REAL FINDING — inspection without a witness mark is not inspection.** "I'll check
  them after a few flights" fails on method, not on principle: putting a hex key in a screw
  and feeling for movement **destroys the evidence you are looking for** — you cannot tell
  whether it was already loose or whether you just broke the seal. Fix: draw a **witness
  mark** (paint pen or nail polish) as a single line across each screw head and onto the
  adjacent motor base. A **glance** then shows rotation, no tool and no ambiguity. This is
  strictly better than a torque check and takes 2 minutes for all 16 screws.
- **Decision.** Do **both**: blue threadlocker, plus witness marks on all 16 motor screws,
  inspected visually **before every flight** for the first five, then per flight day.
  Threadlocker does not replace inspection; it makes the inspection interval sane. Flying the
  low maiden hover *without* threadlocker is acceptable **if** the witness marks are on and
  checked between packs — repeated ≥9 m/s AUTO legs are not.
- **Procurement note:** blue threadlocker is not separately tracked — it appears only inside
  the bundled "Build consumables kit" row (`docs/hardware_order_list.md:304`, $35) and is
  **not confirmed in hand**. If it is not in the box, a $6 tube is the cheapest item on the
  critical path to a flying target drone.

## ADR-0093 — Sizing the own-state age gate from brn-05: 0.25 s as a STALL detector, deliberately not tuned to the idle bench (head decision, 2026-07-29)

- **Context.** `GuidanceConfig.own_state_max_age_s` shipped as `None` (OFF) with a fully
  implemented enforcement path behind it (`own_state_status` → `"own_state_stale"`), because
  picking the number before measuring it would have been inventing the quantity bench
  **brn-05** existed to produce. brn-05 passed on 2026-07-29 and produced it.
- **Measured.** Real 6C Mini ↔ Pi 5 TELEM2 link, props off, 300 setpoints over 15.3 s: every
  logged `own_age_s` fell in **0.00–0.02 s, max 0.02 s**
  (`runs/brn05_bench/deploy_seeker_bench_20260729T230827Z.log`).
- **Decision: 0.25 s**, gate ON.
- **Why NOT ~0.02–0.05 s, which the measurement superficially supports.** brn-05 ran on an
  **idle** Pi with a *synthetic* detector. In flight the same four cores also carry the
  detector (ADR-0090 measured tag decode alone at ~60% of them at full rate), guidance and
  `mavsdk_server`, so the flight `own_age` distribution is necessarily **worse** than the
  bench one. This is the project's own standing rule — *a threshold validated at one
  operating point is not validated at another* — and 0.02 s is an idle-bench number. The
  asymmetry of harm decides it: this gate's action is **refusing to steer**, so a false
  positive costs guidance in the terminal phase, while a false negative costs one stale
  attitude solution. It should therefore be a **stall detector** (is the own-state feed
  *dead*?), not a jitter policeman.
- **Why 0.25 s specifically.** (1) **12.5× the measured max**, so healthy scheduling jitter
  cannot reach it. (2) It **matches `v_perp_stale_s = 0.25`**, already chosen as ≥3 detector
  periods at the measured ~14 Hz onboard cadence — one staleness story instead of two. (3) It
  is comfortably **under PX4's `COM_OF_LOSS_T` (1.0 s)**, so we notice before PX4 drops
  OFFBOARD; a bound above that could only be reached after PX4 had already given up.
- **PRE-REGISTERED, before any flight log exists.** If flight logs show `own_age` approaching
  0.25 s, the finding is that **the Pi is overloaded and work must be shed** — *not* that the
  threshold should be raised. If this ever needs to be a tight bound rather than a stall
  detector, it must first be re-measured **under flight-representative CPU load**. `None`
  remains supported as a deliberate bench-experiment opt-out.
- **Effect observed, not asserted** (`tests/test_own_state_age_gate.py`, 15 checks, and
  nothing referenced this constant before today). Mutation-tested with bytecode caching
  disabled: `None` → 4 fail, `0.02` → 4 fail (the healthy 0.05/0.1/0.24 s ages get refused,
  which is exactly the flight failure mode the sizing defends against), `1.5` → 1 fail (the
  `COM_OF_LOSS_T` bound), `0.25` → 15 pass. Full suite 519 passed / 3 skipped.
- **METHOD NOTE worth keeping — the first mutation run was INVALID and said so only under
  scrutiny.** `None`, `0.25` and `0.02` are all exactly four characters, so the source file
  size never changed; with the mtimes landing in the same second, CPython's `.pyc` staleness
  check (source mtime + size) could not distinguish them and kept serving stale bytecode.
  Two "mutants" therefore ran the *first* mutant's code and the restored file still reported
  `None`. Any future mutation check on a single literal must clear `__pycache__` and run
  `-B`, **and assert that the IMPORTED value equals the source** before trusting the result.
  This is the instrument-is-evidence rule applied to the test harness itself.
- **Date:** 2026-07-29.

## ADR-0095 — The seventh instrument-layer defect was in the CORRECTION to the sixth: `gt_cam_z − alt_m` is not a lever arm (2026-08-10)
- **Context:** Issue #8 reported that the CPA scorer ranges to the camera lens, "verified at **+0.208 m above the airframe datum**, median over 1,748 ticks", and that re-scoring centre-to-centre would move the adopted config from 3/16 to **12/16** inside the 0.35 m ram radius — reversing the project's headline that no camera-guided intercept has reached contact range. Re-measured at the corrected c2c CPA over 168 flights: **median −0.374 m**, against −0.375 m at the camera. It does not move. With horizontal at 0.174 m, **vertical is essentially the whole miss** — on a vehicle whose lead solve is explicitly 2-D horizontal and whose camera measures target elevation every frame and discards it.

It scores 13/16: a *larger* bias than the camera reference it replaces, in the **flattering** direction. A fix for a wrong ruler that would have installed a worse one, and it would have shipped looking like a correction.
- **Why the third pass caught what two did not:** `rescore_cpa.py` had to state its datum explicitly to compute anything, and it carries a **pad-z self-check** (on-pad `gt_cam_z` vs collision rest height + the assumed lever) that fails closed. ## ADR-0096 — Wind is modelled as a world-side drag force via gz ApplyLinkWrench; the interceptor CANNOT correct for it in flight, and that is the finding (2026-08-10)
- **Context:** the contract's `zero-wind-environment` assumption has said since it was written that wind is unmodelled everywhere, that it perturbs the open-loop dash AND rotates the airframe (moving where the camera wedge points), and that the mitigation is a sim wind arm. The builder asked for wind and error correction to be built. This ADR is that mitigation.
- **Decision — mechanism:** a standalone `scripts/wind_driver.py`, in the same architectural category as `m4_target_mover.py` (a world-side process that reads gz state to APPLY physics and never feeds guidance). It finite-differences the interceptor's pose on **sim time** at 20 Hz, computes relative air velocity, and applies PX4's own multicopter drag form `F = m·(MCOEF·|Δv| + ρ|Δv|²/(2·BCOEF))·Δv̂` (`params_drag.yaml` defaults MCOEF 0.15 s⁻¹, BCOEF 100 kg/m²; m = 2.114 kg from the x500 SDF) as an `EntityWrench`. **Default OFF and byte-identical** — `WIND_ARGS` empty means the driver is never spawned.
- **Wind field:** steady vector + **Dryden** low-altitude turbulence (horizontal only; `w_z = 0` declared), the standard Gauss-Markov discrete form from MIL-HDBK-1797. Tiers are **sourced to the Beaufort scale**, not invented: BEST 1.5 m/s (top of Bft 1), EXPECTED 4.5 m/s (mid Bft 3; PX4's own reference `windy.sdf` uses 5.4 m/s as an adjacent anchor), WORST-credible 8.0 m/s (bottom of Bft 5 — and written into the field protocol as the **no-fly ceiling**, so sim coverage and field exposure coincide).
- **Rejected routes, recorded so they are not re-tried:** the bare `<wind>` SDF element (momentum-drag only, 0.48–0.71× the PX4-model force, no gusts, one constant per world file); the WindEffects plugin (needs a `server.config` symlink swap, and world-SDF placement silently kills Physics/IMU/camera — a measured trap); a PX4-side wind parameter (does not exist for gz); runtime system-add (returned success and produced zero force).
- **THE HONEST FINDING, and it is the most valuable output here: the interceptor cannot correct for wind in flight.** After the cue latches the link dies, the dash is open-loop, and the only wind signal a real vehicle could have is *what the operator measured before launch*. So the "correction" is a **pre-flight constant**: `--wind-trim-mps` / `--wind-trim-dir-deg` adjust what the **lead solve assumes the vehicle will achieve**, and nothing else. The commanded dash speed is untouched — commanding less speed into a headwind makes the sag worse. No live wind value of any kind enters the tick loop. That was pre-authorised in the design brief ("if the honest answer is that only the terminal camera phase can correct, say so — that is a finding, not a failure") and it is what came back.
- **A BLOCKING DEFECT THE REVIEW CAUGHT, worth recording because of its shape:** the driver published to `/world/<w>/wrench/persistent` every tick. gz-sim's `ApplyLinkWrench` does **not replace** a persistent wrench — `OnWrenchPersistent` does `persistentWrenches.push_back(_msg)` unconditionally and `PreUpdate` applies **every** entry (verified against the gz-sim8 upstream source, matching the installed 8.14.0). At 20 Hz over a 30 s flight that is ~600 superimposed wrenches: a force ramping **linearly with time**. It would not have looked like a bug — it would have looked like "the wind builds during the dash" — and **the driver's CSV logs the INTENDED force, so the log would have looked perfect while the physics diverged.** A paired control could not have caught it; both arms share the driver. Fixed by clearing before every publish, fail-loud if the clear fails, with a static guard (`tests/test_wind_driver_wrench.py`, mutant-verified) because the behavioural proof needs a Gazebo boot and will not run per-commit.
- **This is the instrument-defect class one layer down:** not a bug in a *scorer*, but a bug in an **actuator whose log reports intent rather than effect**. Worth generalising: any component that logs what it *commanded* rather than what was *applied* can diverge silently.
- **Assumptions declared (contract `assumptions[]`):** `target-wind-immune` (the teleported target cannot be blown, and its error would be CORRELATED with the interceptor's), `anemometer-wind-cue` (given-noisy; σ is a **placeholder from spec sheets, not measured** on the purchased unit), `wind-sag-table-unmeasured` (the sag table derives from PX4 generic drag defaults, **not this airframe**).
- **NOT YET DONE, and nothing may be quoted until it is:** the **W3 physics probe** — hover in steady 5 m/s, confirm settled tilt-into-wind within ±30% of the derived atan(a_drag/g) ≈ 4–5°, then kill the driver and confirm the force is removed. No wind arm has flown. Every published number in this project still assumes a windless world.

## ADR-0097 — MBSE views are GENERATED from the contract, not hand-modelled in Capella/SysML (2026-08-12)
- **Context:** the builder asked whether a free MBSE (model-based systems engineering) tool could organise the project and double as an interview piece. MBSE means the system lives in one model and the diagrams/documents are *views generated from it*, rather than artefacts maintained in parallel with the build. The candidate free tools were **Capella** (Eclipse, Arcadia method — the name-brand in aerospace, used at Thales/Airbus), **Gaphor** (lightweight pip-installable SysML/UML), **Papyrus** (Eclipse SysML), and the **SysML v2 pilot** (textual, git-diffable). Cameo/MagicDraw is not free.
- **The observation that decided it:** `docs/project_state.json` is *already the model*. It carries the functional chain (`stages` + `edges`), system-level requirements (`constraints`), design decisions with rationale (`decisions`, each keyed to a `stage_id`), the graded assumption register (`assumptions`, each keyed to the stages it feeds via `stages[]` ↔ `stages[].consumes`), verified quantities with provenance (`key_numbers`), and the open-issue ledger (`contradictions`). What was missing was not a model — it was **views** of one.
- **Decision:** generate the views. `scripts/render_mbse.py` renders `docs/mbse.html` — seven views (operational context/system boundary, functional architecture, requirements register, traceability matrix, assumption register, verified quantities, open items) — from the contract, with **no hand-authored content**. Published as a second Artifact (`mbse_artifact_url`, stored in the contract as a new top-level key; `validate()` extended in the same edit per the schema rule).
- **Why NOT Capella, despite the stronger brand:** a hand-maintained model drifts from the build, and **drift is this project's documented failure mode** — the entire contract/drift-check apparatus exists because decisions that lived only in chat evaporated (ADR-0076, the five mirages). A Capella model would be a second source of truth with no mechanism keeping it honest, and a stale systems model shown in an interview is a liability: the first reader who cross-checks it against the repo finds a discrepancy. The generated route inverts that — the model *cannot* disagree with the contract, and the claim "my system model is CI-gated" is itself the stronger interview answer. The cost is the Capella/Arcadia line on the résumé, which is the smaller loss.
- **Enforcement (the part that makes it real):** `render_mbse.py --check` bakes a SHA-256 of the canonical contract into the rendered page and fails if the contract has moved since the render. Wired into `scripts/run_tests.sh` [3/4] beside the dashboard check. **Mutation-verified**: with `updated` perturbed the check exits 1 naming both digests; restored, it exits 0. A check that cannot fail is not a check.
- **Honesty carried into the views, deliberately:** the page leads with a banner stating that 4 of 19 registered inputs are supplied *error-free*, that 5 assumptions are currently `violated`, that every quantity resting on an error-free input is a best-case upper bound, and that **no camera-guided sub-metre intercept of the realistic 3-D target has been demonstrated**. A systems model that omits its own open items is the failure mode being guarded against, not a polished deliverable.
- **Design:** inherits `docs/dashboard.html`'s existing token set (paper ground, Charter/Helvetica/mono roles, the status palette) so the two published Artifacts read as one document set. Diagram edges use collision-aware routing — a straight `sim_harness → coded_dash` line passed through the `pointing` box, drawing a connection the model does not contain.
- **Scope discipline:** this ADDS one script and one generated page and no maintenance burden (the page has no independent state). Rejected as scope growth: a second modelling universe to keep in sync, and any hand-drawn diagram set.

## ADR-0098 — Gazebo DOES apply the wrench; our own driver was cancelling it. Wind arm PARKED by builder ruling (2026-08-29)
- **Context:** ADR-0096 built the sim wind mechanism and closed with a stop sign — *"NOT YET DONE, and nothing may be quoted until it is: the W3 physics probe … No wind arm has flown."* This ADR is that probe's result, and the builder's ruling on what happens next.
- **The probe:** pre-registered in `docs/wind_gate0_prereg.md` and committed BEFORE it flew (8cc2c26), so the criterion provably predates the numbers. Three phases in one flight — driver OFF (level) → driver ON (tilt) → driver EXITED (level again) — with attitude read from **Gazebo ground truth**, not the PX4 estimator, because the question is whether physics moved and an estimator is one more instrument to be wrong. Harness `scripts/check_wind_gate0.sh` → `scripts/wind_gate0_probe.py`; 31 offline tests on the probe's own geometry and verdict logic, because the probe is an instrument.
- **Two defects found before any answer was possible, both in the measurement path:**
  1. **The driver was computing drag from a FROZEN POSITION.** Its pose callback matched the airframe's LINK entity and preferred it over the MODEL. A nested link's pose in gz's pose topics is **relative to its enclosing model**, so `base_link` reads a constant (0, 0, 0.24) — `x500_base`'s declared offset — however the aircraft flies. Measured (`logs/wind_gate0_20260829T154442Z`): a climb to 5.45 m with **all 4789 pose callbacks reporting z = 0.2400**, and `v_veh_n`/`v_veh_e` = 0.00000 in every one of 599 applied rows. Relative air velocity is (wind − vehicle); with the vehicle term structurally zero, a **dash arm would have computed drag from the wind speed alone and omitted the airframe's own ~9 m/s** — wrong by a large factor, with a CSV that looks perfect because it faithfully logs the force that was commanded. **This is ADR-0006's root cause recurring in a new file** — the ADR that says a "same number, different assumed parent" mistake "can bite twice". It did, two months later.
  2. **The probe's own CSV reader** fed the driver's `#` provenance banner to `DictReader` as a header, so a 599-row file read as 0 rows.
- **THE NEAR-MISS, which is the most valuable thing here.** Defect 2 is what saved us. With the pose frozen, all three phases read 0.000° — **indistinguishable from "Gazebo never applied the force."** Had the parser worked, the probe would have returned a confident **NULL and condemned a driver that was working correctly** (598 published, 0 failures, 1.9090 N against a derived 1.909 N). A false null is the most expensive outcome available: it retires a working capability and sends the project back to rejected alternatives. The probe now fails **VOID when the ground-truth pose never moves**, so a frozen instrument can never again be mistaken for a finding about Gazebo.
- **THE ANSWER — Gazebo applies the wrench, essentially exactly.** `scripts/wind_wrench_diag.py` separates the candidate causes in one flight. Arm B — **a single persistent `EntityWrench` on the scoped link name, published once** — produced a settled ground-truth tilt of **5.259° at a lean bearing of 270.2°**, against a derivation of **5.262° at 270.0°**, over a 0.160° baseline (`logs/wrench_diag_20260829_partial/`). Agreement to 0.003° in magnitude and 0.2° in direction. The entity naming is correct, the plugin path is correct, the ENU conversion is correct, and the force is applied at the commanded magnitude.
- **ROOT CAUSE of the NULL: ADR-0096's own fix.** That ADR correctly found that `ApplyLinkWrench` **appends** persistent wrenches (`push_back`) rather than replacing them, and fixed the resulting accumulation by clearing before every publish at 20 Hz. But the clear and the wrench go out on **two different topics** (`/wrench/clear` and `/wrench/persistent`), and gz-transport gives **no ordering guarantee across topics** — so "clear then publish" frequently lands as "publish then clear", leaving nothing applied. Measured end-to-end: the same force that gives 5.259° when published **once** gives **0.167°** when published under the 20 Hz clear+publish recipe (`logs/wind_gate0_20260829T155141Z`). **The fix for one silent defect manufactured the next one, and both had logs that looked perfect** — the accumulation bug and its cure share the property that the error lives upstream of what gets written down.
- **Decision (BUILDER RULING, 2026-08-29): the wind arm is PARKED.** No wind arms fly, no sag table is populated, no `--wind-trim-*` value is quoted. The builder's reasoning: *"the camera pro nav should combat it enough."*
- **Recorded honestly, because the ruling rests on a claim the evidence does not currently support:** wind's dominant damage is to the **open-loop coded dash**, before the camera has a lock — it displaces the aircraft from the aim line AND rotates the airframe, moving where the camera wedge points. The project's own measured headline is that **the camera has not beaten a well-aimed blind dash at any speed or aim error tested**. So "the terminal camera absorbs the wind" is a **declared assumption, not a result** (contract `assumptions[]`: `camera-absorbs-wind`). The ruling is defensible on cost — there is already far more evidence here than the stated purpose needs, and the real risk to this project is that it is never packaged and shown — but the assumption must not later be read as validated.
- **State of the code, so nobody flies it by accident:** `scripts/wind_driver.py` keeps the **pose-entity fix** (that was a genuine bug and is now guarded by three mutation-verified static tests in `tests/test_wind_driver_wrench.py`), and carries a loud STATUS banner recording that its **publish recipe is known-broken and self-cancelling**. It remains **default-OFF and byte-identical** for every existing arm, so nothing in the repo is affected. The one-line-class fix is known and written down below, unspent.
- **If wind is ever unparked, the fix is already identified** — do NOT re-derive it: publish the persistent wrench **once per force change** rather than clearing every tick, or drive the one-shot `/world/<w>/wrench` topic at the physics rate. Arm B proves the first works. Arms C–F of `wind_wrench_diag.py` were cancelled mid-run and would confirm the rest; the script is kept for that reason.
- **Why:** the builder's call on scope stands; the finding is recorded so the next session inherits the answer instead of the mystery.
- **Date:** 2026-08-29.

## ADR-0099 — The vertical channel lands as a DASH TRIM plus an AGL floor, not a terminal law: ADR-0085 was decided and never written (2026-09-10)
- **Context.** The builder asked why a late camera adjustment cannot save a slightly-off aim, having watched exactly that on video, and whether there is really a physics limit on reading the tag and correcting in time. Checking it against the code rather than the headline turned up a gap nobody had recorded: **every seeker computes `bearing_vert_rad` and nothing in `flight/` consumes it.** The elevation enters the derotation chain only to get the HORIZONTAL azimuth right (FIX-A's 3-D ray); the sole vertical command anywhere, in the deployed loop and in the harness that produced every measured arm, is an altitude-hold P-loop to a preset height. Meanwhile **ADR-0085 (2026-07-25) had already DECIDED** "in the terminal, the vertical channel follows the camera-derived target elevation within a bounded band, floored by a hard AGL minimum". Neither half existed: `grep -n "min_agl\|agl_m\|elevation" flight/deploy/real_flight.py` returned nothing, `flight/fov_guidance.py` appeared there only inside the honesty-audit module list (audited, never called), and `ADR-0085` appeared **0 times** in `project_state.json` and **0 times** in `docs/next.md`. Recorded as contradiction `terminal-vertical-channel-decided-not-built`.

So "the camera terminal does not beat a well-aimed open-loop dash" was measured on arms whose guidance was **structurally blind to the dominant error term**.
- **Two measurements taken before deciding anything, both offline from committed logs.**
  - `scripts/forensics/vertical_miss_anatomy.py` — the cue-era fleet is off-altitude at closest approach on **16/16** flights (median **+0.508 m**, i.e. ABOVE the target). ~~and altitude drifts +0.320 m across the dash … the vertical error is DELIVERED BY THE DASH~~ — **RETRACTED 2026-09-10, see the second addendum.** That drift was measured against a baseline pooling every pre-dash tick, including 87–108 `TAKEOFF` ticks, and `alt_m` reads 0.000 on the ground, so it was largely the takeoff climb. ADR-0085's **hard AGL floor** ships with it as a flight-safety backstop that beats the trim rather than averaging with it. Both **default-inert** (`0.0` / `None`) and byte-identical when inert, proven by a test that compares the whole STANDBY→DASH→SAFE setpoint stream tick by tick and also asserts the stream contained non-zero vertical commands, so the comparison cannot be vacuous.
- **Why a trim and not the terminal law ADR-0085 named.** Three reasons, in order of force — **reason (1) is REFUTED, see the second addendum**: (1) ~~the error is delivered by the dash, so the terminal inherits it~~ — measured against a settled baseline the dash delivers −0.019 m, a 10% term, so this reason does not hold and the trim is a 10% lever, not the fix; (2) the terminal has 0.02–0.17 m of authority on the tag path and cannot null a ~0.4 m delivered offset out of that; (3) the project already fixed the HORIZONTAL analogue exactly this way — ADR-0080 **derived** the coded-dash crossing bias as a pre-flight constant ("DERIVE it, don't tune it") and ADR-0083 adopted a measured +5° trim. `derive_dash_alt_trim_m` takes a measurement as input for the same reason, so a reviewer re-derives it rather than trusting it.

## ADR-0099 addendum (2026-09-10, same day) — an adversarial review found the integration wrong in five ways; all fixed, and two numbers in the ADR above were wrong
- **Why this addendum exists.** ADR-0099 was reviewed before merge by an independent agent with a mandate to break it. It returned **not mergeable as-is**, with five blockers. The helper functions were sound; the INTEGRATION was wrong. Every finding below was CONFIRMED by the reviewer running something, not inferred, and every one is now fixed with a regression test that fails on the original defect. Recording it here because the ADR's own claims were part of what was wrong.
- **F1 — the trim biased the STANDBY hold, and the arm gate compares against the UNTRIMMED config value.** `alt_tol_m` is 0.300 m; the trim this ADR derives is **0.320 m**. So the first GO failed the arm gate and went straight to SAFE, which is absorbing: one GO, mission over, at the exact value published. The reviewer demonstrated the threshold with a `FakeVehicle` sweep (trim −0.29 dashes, −0.31 does not). **Fix:** the trim is a DASH correction and now touches only the dash and terminal references. `_v_down` reverted to its pre-change two-liner. The ten original tests passed because their fixture set `standby_settle_s=0.0` and fired GO before the hold had settled.
- **F2 — the lever was unreachable from every documented run path.** No CLI flag, and `build_config()` never set either field, so `--dry-run`, `--sitl-smoke` and the real driver all ran with it hard-wired off — the phantom-flag class `tests/test_inert_flag_guards.py` exists to prevent. **Fix:** `--dash-alt-trim-m` and `--min-agl-m` added and wired; a dry run with both set walks STANDBY→CODED_DASH→ENGAGE→BREAKOFF→SAFE and passes. **Still open and now stated honestly:** `scripts/m4_intercept.py`, the harness that would fly the pre-registered arms, has no lever at all, so the prereg's "only the flag values change" was false for the sim. The pre-registration now says so.
- **F3 — the hard AGL floor did not cover the guided terminal, BREAKOFF or SAFE, and the "one function / five call sites" claim was false.** `_v_down` has FOUR call sites in three states; ENGAGE returns the SEEKER's own setpoint, and BREAKOFF and SAFE emit hardcoded rates. The reviewer's probe showed ENGAGE commanding **+2.0 m/s down while 2 m under its own floor** — the floor was missing from precisely the state ADR-0085 wrote it for. **Fix:** new `flight.guidance.floor_v_down` applied to the EMITTED command in `_decide`, the one exit every state does funnel through. The false claim is struck from all five places it appeared.
- **F4 — a square wave on the vertical channel.** The coast reference carried the trim and the seeker's own `alt_ref_m` did not, and `_step_engage` alternates between them tick by tick, so the commanded reference jumped by exactly the trim at up to 20 Hz. Worse, the seeker pulled the vehicle back to the untrimmed altitude the moment it locked. **Fix:** the seeker's reference is built from the same trimmed value.
- **F5 — the byte-identity proof was invalid, which is the most embarrassing finding here.** The test compared `cfg()` against `cfg(dash_alt_trim_m=0.0, min_agl_m=None)`: the same class down the same code path, differing only in whether the defaults were spelled out. The commit message's "against a machine that never mentions the fields" described something that did not exist. The reviewer's mutant adding **+0.4 m inside `_v_down` PASSED it**, and a second mutant shifting the standby reference by 0.4 m passed the **entire 105-test suite**. **Fix:** the identity tests now compute the expected command INDEPENDENTLY from the config (`_expected_hold_v_down`). Both of the reviewer's mutants, plus removing the floor and reverting the coast reference, now fail — verified by re-running all four.
- **Two numbers in the ADR above were wrong, and finding out why exposed a bug in my own instrument.** The reviewer asked why `vertical_miss_anatomy.py` reported 24 measured flights where its sibling `handoff_closing_speed.py` reported 16 over the same directory. Chasing it: the vertical tool **never checked that the chosen dash phase is present**, so eight files carrying NEITHER dash phase fell through, found a CPA anyway, produced a null drift, and were still **counted as measured flights**. The sibling always had that guard, and the disagreement between the two was the tell. Corrected: **16/16** flights, median vertical **+0.508 m**, and the drift share restated as the **PAIRED per-flight median, 72%**, rather than a ratio of two medians taken over two different populations. The direction and the conclusion are unchanged; the arithmetic was not.
- **Also fixed:** NaN now fails CLOSED on the safety floor and on the derived trim (`out < floor` is False for NaN, so a NaN sailed straight past the backstop); `share` is bounded to [0, 1] so it cannot become the unbounded tuning knob its own comment forbids; `MissionConfig` gained a vertical validator that refuses a floor at or above the references it would truncate; the flight CSV gained `alt_ref_m` and `floor_active`, because without them a trimmed flight's log was byte-indistinguishable from an untrimmed one and the documented procedure re-derives the drift FROM these logs; the misnamed `sag` variable is now `drift` with its inverted comment fixed, since a human transcribes that number into a trim whose wrong sign doubles the error; and a tautological assertion (`assert out is ref or isinstance(out, float)`) is gone.
- **A validator I wrote and then had to correct myself.** The first version refused `|trim| >= alt_tol_m`, which reads plausibly and is wrong: it ties the trim to the ARM GATE's tolerance, two unrelated quantities, and it rejected −0.320 m — the exact value this ADR derives. A validator that refuses the project's own documented experiment is worse than the defect it guards. The gate coupling was the real bug and it was fixed structurally; the magnitude rule is now genuine incoherence only.
- **Status unchanged in the one way that matters: NOTHING HAS FLOWN.** The review does not make the lever validated, it makes it correct enough to be worth flying. Suite 764 passed / 0 failed, honesty audit PASS, both drift checks green.
- **Date.** 2026-09-10.

- **SECOND ADDENDUM (2026-09-10) — ADR-0099's REASON (1) IS REFUTED BY A FIX TO MY OWN INSTRUMENT, and a second lever is registered.** Two adversarial reviews of the work above found nine substantive defects; the two that matter most were in the MEASUREMENT, which is the class this project keeps re-learning (`docs/error_handling_policy.md`, the instruments-are-evidence rule).
  - **The baseline was the takeoff.** `vertical_miss_anatomy.py` defined the pre-dash baseline as "the median of every tick before the dash". On this fleet that pools 87–108 `TAKEOFF` ticks with 21–24 settled `CUE_WAIT` ticks, and `alt_m` is AGL against the arm point — it reads **0.000 on the ground** (the `TAKEOFF` median is +0.005 m). So the reported "+0.320 m of dash altitude drift" was mostly **the vehicle leaving the ground**. Against a settled hover the drift is **−0.019 m**, robust from −0.012 to −0.025 m across six baseline windows (the tool now prints that sensitivity sweep rather than leaving its own creep warning hanging). The baseline now excludes climb phases and **fails closed** when no settled pre-dash hover exists — which is the coded-dash case (`TAKEOFF → CODED_DASH`, no hover), where the old code would have handed `derive_dash_alt_trim_m` a ~+1 m fiction. The tool also crashed with `NameError: name 'sags' is not defined` before printing its verdict, an incomplete rename of mine.
  - **The vertical error is not delivered by the dash.** An additive per-flight decomposition (exact on 16/16 flights), paired per-flight medians, n=13: `origin` (settled pre-dash separation) **+0.127 m / 23%**, `dash_delta` **+0.012 m / 10%**, `post_dash_delta` **+0.348 m / 66%**. **Reason (1) above is refuted** and `dash_alt_trim_m` is a 10% lever. The shares were first printed as a ratio of medians (2% for the dash) — the very error the first addendum was written to fix, repeated on the next number, and it understated the term the trim addresses by 5×.
  - **`origin` is a two-datum mismatch and the cheapest 23% in the project.** `ALT_REF_M = 0.5` is AGL above the arm point; the target's altitude is world z. Nothing reconciles the ~0.22 m the camera sits above ground at rest. It is real separation and cannot be subtracted from a miss, but it is **aim, not guidance** — putting both references in one frame removes 23% of the vertical error with a one-line scenario change. This is the highest-value item the analysis produced.
  - **A quarter of the post-handoff term is not the airframe.** `gt_cam_z − alt_m` should be a constant geometric offset; it moves **+0.033 m** hover→dash-tail and **+0.087 m** hover→CPA — **24% of `post_dash_delta`** — because the camera rides a forward boom that lifts under pitch. The tool's docstring had asserted the opposite ("the 0.120 m camera offset is HORIZONTAL and does not enter a vertical measurement"), true only while level. It also promised an `alt_drift` vs `dash_delta` cross-check that no code implemented; the check is now real and the two **do** disagree (−0.019 vs +0.044 m), which is this lever arm, not the target (`gt_tag_z == 0.500` on every tick of every flight).
  - **A new lever, `--dropout-hold-vertical`, registered with a NULL prediction.** ENGAGE recomputes its altitude hold on every tick with a fresh detection (`cmd_vd` matches the P-loop on 150/150) and abandons it on a dropout — the far branch issues an all-zero setpoint and stores it as `last_cmd`, the near branch re-issues that zero. Vertical zeroed on **0/150** ticks with a detection, **792/877** without, latching for the terminal on **10 of the 14 flights that reached ENGAGE** (2 of 16 never engaged; the denominator is 14, not 16). **But this fleet cannot attribute the excursion to it:** the same branch zeroes the horizontal on the *same* 792 ticks (vertical-only 0, horizontal-only 0 — perfectly collinear) and that is a **16.00 m/s → 0** full-stop brake, a much larger candidate for a climb; and on the 4 flights whose vertical command *survived*, the vehicle climbed **0.28–0.65 m anyway while commanding a descent** (post-handoff term +0.429 m at n=4 vs +0.498 m at n=10 — indistinguishable). So the case for the fix is **architectural** — `alt_m` is own-state, so abandoning the hold during a *camera* dropout buys no robustness — and the registered prediction is a **null**, with the arm required to run as a 2×2 with `--terminal-coast-gate` because a vertical-only arm is not identifiable. Pre-registration: `docs/vertical_channel_prereg.md` §8. The code comment and CLI help had claimed to be pre-registered there while the section did not exist; that section is now written.
  - **A prior question neither lever answers.** The altitude loop shows a persistent **≈ −0.087 m steady-state error in hover** while continuously commanding −0.087 m/s and gaining ~0.001 m — the commanded vertical velocity is not being delivered. Both levers assume that loop has authority. Not root-causable without a sim run; it should be measured before either is priced.
  - **Smaller corrections, each mutation-verified.** `_clamp(nan, ±0.5)` returns **+0.5**, so a NaN altitude was laundered into a full-rate DESCEND before reaching the new NaN guard — the call site now tests `alt_m == alt_m`. The lever no longer fires on an abort tick and refreshes `last_cmd` so it still means "the last command emitted". Seven new tests sat *after* the `__main__` block and were absent from the file's `ALL` list, so script mode reported **43/43 out of 50** — a self-test under-reporting its own coverage; they are moved, registered, and a guard now fails if `ALL` ever drifts again. The wiring test asserted only the call *count*, which would have passed with the call moved out of the dropout branch; it now asserts the enclosing scope. A cwd-relative path in `flight/tests/` is repo-root anchored. `floor_v_down`'s docstring claimed project-wide coverage but is wired only in `real_flight._decide` — the same over-broad "one function" claim F3 already retracted once — and `_floor_active` could report a stale True (latent: no current path feeds `_decide` a `None` setpoint, so this is hygiene and the test is a contract test, not a reproduction).
  - **Scope on every number above.** Cue-era two-stage `--handoff` fleet of 2026-07-09, phase `DASH`, **not** `CODED_DASH` — off the adopted configuration; 2 of 16 never engaged; the terminal carried a detection on **155 of 1032 ENGAGE ticks (15%)**, so these terminals were mostly hovering rather than seeking. ## ADR-0100 — The height reference is lowered by the vehicle's own rest height: 2/16 → 13/16 inside the contact radius, best-case (2026-09-16)

- **Context.** The altitude hold regulates the vehicle's *estimated height above its arm point* to 0.5 m; the sim target's centre is at world z = 0.5 m. The airframe rests 0.229 m above the ground on its gear, so "0.5 m" on the vehicle's own scale is ~0.73 m in the world. Nothing ever lined the two up. First seen offline (ADR-0099 second addendum, "origin, 23%"), then measured in flight on the dev machine, then pre-registered (docs/vertical_channel_prereg.md §9) before any arm flew. Along the way a sign error was caught: docs/flight_plan_candidates.md said the adopted arm flies BELOW the target; the per-tick logs say ABOVE.
- **Options.** (a) leave it and build vertical steering first (ADR-0085, never written); (b) raise the target in the scenario; (c) a default-OFF flag that shifts the vehicle's reference by a pre-flight constant of its own geometry. Chose (c): it is the only one that maps to something a real operator does with a tape measure, and it leaves every historical baseline reproducible.
- **Decision.** `--alt-ref-offset-m -0.207` (0.2290 m rest height − 0.022 m hover error) joins the ADOPTED coded-dash config (`AE5dashZ` in scripts/experiments/flight_plans/run_arm.sh). The code default stays 0.0, so the M0–M5 tag gates are untouched.
- **Evidence.** Two disjoint seeds (456, 789), n = 8 paired flights each, dash-only, primary ruler (airframe centre, interpolated): inside 0.35 m **2/16 → 13/16**; medians 0.563→0.215 m and 0.457→0.249 m; B closer on 14/16 pairs; median vertical fell 0.227 / 0.200 m against 0.207 m commanded. Pre-registered criterion (≥6/8, ≥0.10 m) met on both.
- **What this is NOT.** Not a camera-guided kill (camera off in both arms). Not a transferable number: it leans on two given-perfect inputs — the launch aim (`launch-cue-error-free`) and the target's exactly-known height (`target-height-known`, registered today). It is a **best-case upper bound on a ballistic pass**. A real threat's height is a guess, and with no vertical steering in the terminal a height error passes straight into the miss — which is now the strongest argument yet for building ADR-0085's vertical channel.
- **Open.** (1) B still ends ~0.19 m high: the vehicle climbs during the dash at −41° to −45° pitch (first visible today, via the new attitude columns). (2) Flight index #4 got worse in both B arms and carries a `yaw-check` flag only there. (3) Target-height error injection (±0.25/0.5/1 m) is the honest follow-up and is scheduled in the assumptions register.

## ADR-0101 — The terminal ends on the vehicle's own motion, not on the camera's range: the PASSAGE WINDOW (2026-09-17)
